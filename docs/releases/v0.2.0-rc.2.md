# v0.2.0-rc.2: compute optimization validation

Development candidate, measured 2026-10-16. This is a code validation report;
no new release tag or benchmark checkpoint release has been published.
All four original full training jobs were stopped at the user's request.
Only bounded benchmarks, two-update checkpoint checks and memory stress checks
were run after that decision. Full training has not been restarted.

The later [geometry follow-up](v0.2.0-rc.2-geometry.md) reports additional
matched throughput in samples/s. It also corrects a wiring omission: this
first-round code contained target-spectrum caching, but the main validation
metric call did not forward that cache. The follow-up activates it. All
historical measurements below remain unchanged.

## Training update time

All models use the corrected ordering. O(3)-s also averages identity/inversion.
The effective batch remains 32. Native Muon starts at 1e-3; norm, embedding and
other unsupported parameters use AdamW at 1e-4. The official QH9Stable random
split, objective, precision and schedule are unchanged.

| QHFlow2-s | 32 × 1 → 32 × 1 | 0.320 | 0.278 | **12.9%** | 7.0% |

| QHFlow2-l | 4 × 8 → 16 × 2 | 1.842 | 1.118 | **39.3%** | 5.8% |

The last column compares optimized eager and compiled code at identical
microbatch size. The overall gains include larger microbatches for O(3)-s, m
and l, in addition to source changes. Timing includes forward, backward,
gradient clipping and the optimizer update, and excludes loading and validation.
These are medians of six measured updates after two warmups, using the same
32 official training rows and fresh model processes. They are not measurements
of complete epoch or 260k-step training wall time, nor of model accuracy.

Hardware: H100 80GB HBM3, PyTorch 2.11.0+cu126, float32, TF32 disabled.
Original-versus-eager measurements used GPU 4; eager-versus-compiled measurements
used GPU 3 on the same server. Thus the overall before/after columns cross two
identical-model GPUs. Each job excluded co-resident GPU work through a queue
lease and checked for foreign GPU processes around every timed update.

## Compilation and implementation

Use the lean Hamiltonian-only preset `config_stable_muon_optimized.yaml`.
It skips unused Q tensors and cut orbital coefficients, enables pinned memory
and persistent workers, and rejects incompatible loss configurations.

The implementation caches constant coupling/noise operators, vectorizes AO
cutting and reconstruction and reverse edges, avoids unnecessary data copies
and validation trajectories, and reuses target eigenspectra and overlap factors
within a validation batch. Nonpersistent caches preserve checkpoint keys.

The [maloQ flash compilation boundary](https://github.com/manasakani/maloq/blob/4d4c588604e9844a4cfcd460fa61e3463dcf4142/src/maloq/helm/common/compile.py)
and [compile tests](https://github.com/manasakani/maloq/blob/4d4c588604e9844a4cfcd460fa61e3463dcf4142/tests/test_torch_compile.py)
informed the selective tensor-module compilation and verification strategy.
Graph construction and geometry stay eager. Backbone blocks, contraction heads,
AO expansion and noise expansion compile with `dynamic=True, fullgraph=True`.
No FlashSO2 architecture, weights or Wigner kernels were imported.

A three-input einsum let opt_einsum choose paths from symbolic batch sizes,
causing specialization despite dynamic mode. Two fixed pairwise contractions
remove that shape-dependent path selection. The three tested graph batches now
produce stable unique-graph counts: 13/13/13 for s, O(3)-s and m; 12/12/12 for l.
This validates the tested shapes, not an unlimited guarantee against recompilation.

Call this after constructing the Lightning module and before fitting:

```python
from common.compile import compile_flow
compile_flow(lit_model, scope="blocks")
```

The prepared queue resume launcher accepts `QHF_COMPILE_SCOPE=blocks`.
Compilation remains explicit opt-in. Whole-model compilation encounters the
radius-graph boundary; compiling native Muon was slower in the tested runtime.
A batched Muon prototype failed the update-equivalence tolerance and was removed.
The selected optimizer remains native Muon plus AdamW.

## Correctness and checkpoint continuation

- 82 tests passed at measured commit `86e2ebb3e612dbf9ebc4bdf989ac557deed8e58d`.
- Original-versus-optimized initial loss and every parameter gradient matched
  at fixed microbatch and RNG seed: maximum gradient difference 2.10e-9.
- Compiled-versus-eager initial loss and every parameter gradient passed the
  same checks; gradient tolerances were rtol 3e-4, atol 2e-6.
- CUDA rotation/inversion checks passed for all four compiled configurations;
  maximum absolute transformation error was 3.21e-7 on the tested molecules.
- All four checkpoint smoke checks restored model weights strictly and checked
  every optimizer tensor and scheduler state exactly before taking two updates.
  Their saved checkpoints reloaded successfully. s/O(3)-s/m used `20f187dc`;
  l used `86e2ebb3`. The latter only changes the contraction evaluation order
  for dynamic compilation and the benchmark guard; parameter names are unchanged.
- Changing microbatch size migrates Lightning's batch-progress counters while
  preserving optimizer-step count. The shuffled loader is not stateful, so
  resumed sample order is not a bitwise continuation of the interrupted run.

The original O(3) sampler indexed latent fields that the projected model omits.
Its training loss was valid, but affected validation omitted sampling/orbital
metrics after a KeyError. This is fixed and regression-tested. Baseline O(3)
validation time is therefore excluded from speedup claims.

The latest original recovery checkpoints remain at steps s=6000, O(3)-s=6000,
m=2000 and l=1000. The O(3) smoke used an earlier saved step 5000; it did not
replace the latest original checkpoint. Queue exit status `complete` reflects
graceful shutdown, not completed scientific training. No new convergence or
benchmark-accuracy claim follows from these short checks.
